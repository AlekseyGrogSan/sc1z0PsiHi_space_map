# 👥 План разделения бэкенд-разработки на 3 человек
## Проект: «Карта пространства» (FastAPI + PostgreSQL + MinIO)

---

## 🏗 Архитектурное разделение зон ответственности

Чтобы разработка шла параллельно без взаимных блокировок и конфликтов слияния в Git, система разделена на **3 независимых функциональных домена**:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   👤 РАЗРАБОТЧИК 1: Core, Auth & Spaces                │
│  - Скелет проекта, Docker Compose, Alembic                             │
│  - Пользователи, JWT Auth, RBAC (Superadmin, Organizer, Member)        │
│  - Управление Пространствами (Spaces) и Этажами (Floors)               │
│  - Главный кэшируемый агрегатор данных для мобильных: GET /public/...  │
└───────────────────▲────────────────────────────────▲───────────────────┘
                    │                                │
                    │ Интеграция S3-сервиса          │ Интеграция POI и Роутинга
                    ▼                                ▼
┌──────────────────────────────────────┐  ┌──────────────────────────────┐
│  👤 РАЗРАБОТЧИК 2: Media & Panoramas │  │ 👤 РАЗРАБОТЧИК 3: POI & Nav  │
│  - MinIO S3 клиент (Presigned URLs)  │  │  - Точки интереса (POI)      │
│  - Загрузка планов и 360-панорам     │  │  - Граф пешеходных путей     │
│  - Celery/Arq воркер: BlurHash,      │  │  - Алгоритм A* маршрутизации │
│    WebP превью, нарезка Cubemap      │  │  - Многоэтажные переходы     │
│  - Сшивка кадров со смартфона        │  │  - Список шагов и панорам    │
│  - Связи панорам (Hotspots)          │  │    вдоль построенного пути   │
└──────────────────────────────────────┘  └──────────────────────────────┘
```

## 👤 РАЗРАБОТЧИК 1: Core, Auth, Spaces & Public Aggregator
> **Роль**: Архитектор ядра / Lead Backend. Отвечает за фундамент системы, разграничение прав и быстрый публичный API.

### 1. Зона ответственности
- Инициализация репозитория, `docker-compose.yml` (PostgreSQL 16, MinIO, Redis).
- Настройка `pydantic-settings`, базы данных SQLAlchemy 2.0 (asyncpg) и Alembic миграций.
- Модуль пользователей, регистрация, JWT аутентификация (Access + Refresh токены).
- Ролевая модель (RBAC): системный админ (`superadmin`), организатор (`organizer`), члены команды (`owner`, `editor`, `viewer`).
- Управление пространствами (выставки, отели, ТЦ) и публикация карты без смены публичного URL.
- Сборка и отдача оптимизированного JSON для посетителей (`/public/spaces/{slug}`).

### 2. Таблицы базы данных
- `users` (id, email, hashed_password, full_name, system_role, is_active, created_at)
- `space_members` (id, space_id, user_id, role, created_at)
- `spaces` (id, title, slug, description, is_published, settings, created_at)
- `floors` (id, space_id, floor_number, title, width_px, height_px, ppm)

### 3. API Эндпоинты
- `POST /api/v1/auth/register` — регистрация
- `POST /api/v1/auth/login` — получение JWT пары
- `POST /api/v1/auth/refresh` — обновление токенов
- `GET /api/v1/auth/me` — профиль и доступные пространства
- `GET /api/v1/admin/users` — список пользователей (только для `superadmin`)
- `PATCH /api/v1/admin/users/{id}/status` — блокировка организатора
- `POST /api/v1/spaces` — создание пространства
- `GET /api/v1/spaces/{id}` — карточка пространства со списком этажей
- `PATCH /api/v1/spaces/{id}` — редактирование метаданных
- `PATCH /api/v1/spaces/{id}/publish` — публикация / снятие с публикации
- `POST /api/v1/spaces/{id}/members` — добавление редактора в команду
- `POST /api/v1/spaces/{id}/floors` — создание этажа
- `GET /api/v1/public/spaces/{slug}` — публичный бандл для мобильного клиента

## 👤 РАЗРАБОТЧИК 2: Media Engine, MinIO S3 & 360° Panoramas
> **Роль**: Медиа-инженер / Фоновые воркеры. Отвечает за хранение, высокую скорость загрузки тяжелых фото и виртуальный 3D-тур.

### 1. Зона ответственности
- Сервис работы с MinIO (`aioboto3`): создание бакетов `spaces-public` и `spaces-staging`, генерация Presigned S3 PUT/GET URLs.
- Потоки загрузки без нагрузки на память FastAPI (клиент грузит напрямую в S3).
- Воркер асинхронной обработки изображений (Celery или Arq + Redis):
  - Оптимизация 2D-чертежей (сжатие в WebP, расчет размеров `width/height`).
  - Генерация хэш-строки `BlurHash` для мгновенного рендера фона.
  - Создание легковесного `preview.webp` (1024×512, ~50 КБ).
  - Нарезка панорам на кубические тайлы (Cubemap 6 граней) под Marzipano / Pannellum.
  - Пайплайн сшивки серии фото со смартфона (OpenCV Stitcher) в 360° полотно.
- Связывание панорам между собой интерактивными стрелками-переходами (Hotspots).

### 2. Таблицы базы данных
- `panoramas` (id, floor_id, title, x_coord, y_coord, status, blurhash, preview_key, original_key, cubemap_prefix, initial_heading)
- `panorama_hotspots` (id, source_panorama_id, target_panorama_id, yaw, pitch, title)
- `upload_sessions` (id, panorama_id, frame_count, status, created_at)

### 3. API Эндпоинты
- `POST /api/v1/floors/{floor_id}/plan/upload-url` — Presigned URL для загрузки 2D-плана
- `POST /api/v1/floors/{floor_id}/plan/confirm-upload` — подтверждение загрузки плана и запуск рендеринга
- `GET /api/v1/floors/{floor_id}/panoramas` — список панорам этажа
- `POST /api/v1/floors/{floor_id}/panoramas` — привязка точки панорамы к координатам (x, y)
- `POST /api/v1/panoramas/{id}/upload-ready-url` — Presigned URL для готовой 360-фотографии
- `POST /api/v1/panoramas/{id}/stitch-session` — создание сессии загрузки серии кадров со смартфона
- `POST /api/v1/panoramas/{id}/start-processing` — отправка задачи на сшивку/нарезку в воркер
- `GET /api/v1/panoramas/{id}/status` — статус обработки (pending, processing, ready, error)
- `POST /api/v1/panoramas/connections` — добавление стрелки-перехода между двумя панорамами
- `DELETE /api/v1/panoramas/connections/{id}` — удаление перехода
- `GET /api/v1/public/panoramas/{id}` — публичные данные панорамы (Blurhash + ссылки на тайлы)

## 👤 РАЗРАБОТЧИК 3: POI, Навигационный граф & Алгоритм маршрутизации
> **Роль**: Алгоритмист / Indoor Spatial Specialist. Отвечает за семантику помещений и построение оптимальных пешеходных маршрутов.

### 1. Зона ответственности
- Точки интереса (POI): стенды экспонентов, стойки регистрации, туалеты, Wi-Fi, кафе, гардеробы.
- Двойная привязка POI: координаты `(x, y)` на 2D-плане + углы `(yaw, pitch)` для отображения плашки внутри 360-панорамы.
- Загрузка картинок и логотипов для карточек стендов (через S3 сервис Разработчика 2).
- Моделирование графа пешеходных проходов (коридоры, дверные проемы, открытые залы).
- Межэтажные связующие ребра: лестницы, лифты, эскалаторы.
- Алгоритм **A\*** поиска оптимального маршрута:
  - Расчет дистанции в метрах и примерного времени пути.
  - Фильтрация по флагу `wheelchair_accessible_only` (маршрут без лестниц для маломобильных граждан).
  - Сборка цепочки промежуточных панорам вдоль пути (чтобы посетитель мог прокликать и визуально увидеть коридоры).
  - Генерация текстовых шагов навигации («Пройдите 20 м прямо», «Поверните направо к залу Б»).

### 2. Таблицы базы данных
- `pois` (id, floor_id, panorama_id, title, category, description, x_coord, y_coord, yaw_in_panorama, pitch_in_panorama, gallery_keys)
- `nav_nodes` (id, floor_id, panorama_id, x_coord, y_coord, node_type)
- `nav_edges` (id, from_node_id, to_node_id, weight_meters, is_accessible)

### 3. API Эндпоинты
- `GET /api/v1/floors/{floor_id}/pois` — список всех POI этажа
- `POST /api/v1/floors/{floor_id}/pois` — создание точки POI
- `PATCH /api/v1/pois/{id}` — обновление данных стенда/точки
- `DELETE /api/v1/pois/{id}` — удаление POI
- `POST /api/v1/pois/{id}/images/upload-url` — presigned url для фото стенда
- `GET /api/v1/floors/{floor_id}/navigation/graph` — получение графа проходов для 2D-редактора
- `PUT /api/v1/floors/{floor_id}/navigation/graph` — пакетное сохранение вершин и ребер графа
- `POST /api/v1/spaces/{space_id}/navigation/route` — расчет маршрута между двумя точками (A*)

```
              ┌────────────────────────────▼────────────────────────────┐
              │                   СПРИНТ 2: Фичи и логика               │
              │ Дев 1: CRUD этажей, RBAC проверки, публичный роут       │
              │ Дев 2: Воркер (BlurHash, WebP, Cubemap), загрузка панорам│
              │ Дев 3: CRUD POI, сохранение графа, интеграция A* в API  │
              └────────────────────────────┬────────────────────────────┘

              ┌────────────────────────────▼────────────────────────────┐
              │                   СПРИНТ 3: Стыковка и Релиз            │

              │ Оптимизация кэширования Nginx, документация OpenAPI/Docs│
              │ Передача готового API фронтенд-разработчикам            │
              └─────────────────────────────────────────────────────────┘
```

### Правила совместной работы:
1. **Единый тип первичных ключей**: Все сущности используют `UUIDv4`.
2. **Никаких относительных путей в базе**: Хранятся только S3-ключи без указания хоста (`spaces/1/floors/2/plan.webp`).
3. **Pydantic DTO как контракт**: Если Разработчику 3 нужны панорамы для маршрута, он использует схему `PanoramaShortRead`, которую зафиксировал Разработчик 2 в первый день.
